## 3. Compatibilidade com a stack alvo

### 3.1 Node 22 LTS

Sem incompatibilidade. `tsconfig.json` do backend compila para `target: ES2023`/`lib: ES2023`,
totalmente suportado pelo Node 22. Nenhuma dependência exige Node além de 18+. O ambiente
local de desenvolvimento roda Node 26 (versão corrente, não-LTS) — isso é normal e não afeta
produção, já que o JS compilado é padrão ES2023, não código específico de versão de Node.

**Recomendação (não aplicada — alteraria arquivo existente sem necessidade imediata):**
adicionar `"engines": { "node": ">=22 <23" }` em `portal-backend/package.json` e
`portal-frontend/package.json`. Ajuda a pegar cedo um deploy acidental em versão errada de
Node. Aplicar só se você aprovar.

### 3.2 PostgreSQL 16

Sem incompatibilidade técnica — mas ver o gap do §3.4 antes de interpretar isso como "pronto
para usar".

### 3.3 PM2 / Nginx

Sem incompatibilidade. Processo único (`portal-backend`), sem cluster mode necessário no
volume atual. Nginx serve o frontend como estático e faz proxy reverso do backend — desenho
padrão, sem particularidade do projeto que exija configuração incomum.

### 3.4 Gap crítico — Postgres 16 vs. código real (declarar, não presumir)

Por instrução deste projeto (`ADR-003`, `CLAUDE.md`), não posso presumir uma integração de
banco de dados que não existe no código. Fato verificado: `portal-backend` não importa `pg`,
não tem Prisma/Sequelize/Knex/TypeORM/Drizzle, não lê `DATABASE_URL`, e não tem nenhuma pasta
de migrations. Toda persistência é em memória — decisão já registrada como deliberada em
`START_HERE_NEXT_SESSION.md` (linha "Persistência 100% em memória (decisão deliberada, não
uma lacuna)").

**Decisão tomada para este plano de deploy:** como você pediu explicitamente PostgreSQL 16 na
stack da VPS, o plano abaixo **provisiona o Postgres na VPS** (infraestrutura pronta), mas os
arquivos gerados (`deploy/.env.example`, `deploy/backup.sh`) deixam explícito que **o código
atual não consome esse banco**. Isso não é uma mudança de arquitetura nem uma decisão de
domínio — é só infraestrutura disponível para quando (e se) uma migração de persistência for
decidida via ADR próprio. Se a intenção era diferente (ex.: você já sabia disso e quer pular o
Postgres neste primeiro deploy), me avise antes de rodar o provisionamento do banco.

## 5. Bloqueio conhecido antes do passo de HTTPS

`deploy/nginx.conf` e `deploy/.env.example` usam o placeholder `SEU_DOMINIO_AQUI`. Certbot não
emite certificado Let's Encrypt para um IP nu (`177.153.66.11`) — é necessário um domínio (ou
subdomínio) com registro DNS tipo A apontando para esse IP antes de rodar o passo de HTTPS do
plano abaixo. Isso também afeta `GOOGLE_REDIRECT_URI` (precisa do domínio real cadastrado no
Google Cloud Console como redirect URI autorizado). Quando o domínio existir, é uma
substituição de texto nesses dois arquivos, nada estrutural.

## 6. Plano de deploy — Ubuntu 24.04 (a executar quando o SSH estiver disponível)

Ordem pensada para rodar em poucos minutos, sem decisões pendentes no meio:

1. **Acesso** — confirmar chave SSH (`~/.ssh/dodo_vps_ed25519`) funcionando, criar usuário
   não-root de deploy (ex.: `dodo`) com sudo, opcionalmente restringir login root por senha.
2. **Atualização do sistema** — `apt update && apt upgrade -y`.
3. **Firewall (ufw)** — permitir OpenSSH, 80, 443; `ufw enable`.
4. **Node 22 LTS** — instalar via repositório NodeSource (`setup_22.x`) + `apt install nodejs`.
5. **PostgreSQL 16** — `apt install postgresql postgresql-contrib` (Ubuntu 24.04/"noble" já
   traz Postgres 16 no repositório padrão). Criar role `dodo_app` + database `dodo_portal`
   restritos a `127.0.0.1` (ver ressalva §3.4 — infraestrutura pronta, não consumida ainda).
6. **Nginx** — `apt install nginx`.
7. **PM2** — `npm install -g pm2`.
8. **Certbot** — `apt install certbot python3-certbot-nginx` (só é executado depois de
   confirmar o domínio, §5).
9. **Clonar o repositório** em `/opt/dodo-portal` (ou local equivalente) com o usuário `dodo`.
10. **Preencher `.env`** — copiar `deploy/.env.example` para `portal-backend/.env` e
    `portal-frontend/.env`, preencher `SESSION_SECRET`, credenciais Google OIDC de produção e
    o domínio real.
11. **Ativar `deploy/nginx.conf`** — copiar para `/etc/nginx/sites-available/dodo-portal.conf`,
    symlink em `sites-enabled`, `nginx -t`, `systemctl reload nginx`.
12. **Rodar `./deploy/deploy.sh`** — instala deps, builda os dois projetos, publica o frontend,
    sobe o backend via PM2 (`ecosystem.config.cjs`), recarrega Nginx.
13. **`pm2 startup` + `pm2 save`** — garante que o backend volta sozinho num reboot da VPS.
14. **Certbot** — `certbot --nginx -d SEU_DOMINIO_AQUI` (só após DNS do domínio confirmado).
15. **Validar** — `./deploy/healthcheck.sh SEU_DOMINIO_AQUI`.
16. **Agendar `deploy/backup.sh`** via `crontab` do usuário `dodo` (ex.: diário às 3h).
